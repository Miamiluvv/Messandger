# Безопасность приложения

Документ описывает реализованные в корпоративном мессенджере ДГИ меры по обеспечению информационной безопасности.

## 1. Аутентификация и управление сессиями

- **JWT-токены.** Сервер выдаёт подписанный HMAC-SHA256 токен с идентификатором пользователя в `sub` и сроком жизни. Токен передаётся в заголовке `Authorization: Bearer <token>` для REST-вызовов и в query-параметре `token` при установлении WebSocket-соединения. Подпись проверяется при каждом запросе и при подключении к `/ws`.
- **Хеширование паролей.** Все пароли хранятся в виде хеша **bcrypt** (через `passlib`). Соль уникальна для каждого пользователя; восстановление исходного пароля невозможно.
- **Политика срока действия пароля.** Поле `password_expires_at` ограничивает срок жизни пароля 90 днями. По истечении срока вход разрешён, но клиент получает флаг `password_expired=true` и принудительно перенаправляется на форму смены пароля.
- **Блокировка и заморозка учётной записи.** Администратор может заблокировать (`is_blocked`) или временно заморозить (`is_frozen`) пользователя — оба состояния проверяются на каждом входе.

## 2. Защита от перебора (brute-force)

Реализовано в `backend/app/routers/auth.py`:

- Каждая комбинация **e-mail + IP-адрес** учитывается отдельно.
- После **5 неудачных попыток** входа подряд комбинация блокируется на **15 минут** — сервер отвечает `HTTP 429 Too Many Requests`.
- Счётчик сбрасывается при успешной авторизации.

## 3. Авторизация и разграничение ролей

- **RBAC-модель** с ролями `super_admin`, `admin`, `head`, `deputy_head`, `member`, `readonly`.
- Все администраторские эндпоинты обёрнуты проверкой `current_user.role in ("super_admin", "admin")`.
- На уровне чатов используется ChatMember.role: `owner` / `admin` / `member` / `readonly`. Отправлять сообщения в новостной канал может только владелец/администратор; рядовые участники имеют доступ только на чтение.
- Автоматическое повышение прав: при добавлении в групповой чат начальников управлений и заместителей им автоматически назначается роль `admin` в этом чате.

## 4. Подтверждение деструктивных операций

В клиенте реализован глобальный диалог подтверждения (`ConfirmDialog` + `useConfirmStore`). Перед любым удалением — сообщения, участника чата, уведомления, перед блокировкой/заморозкой пользователя или сбросом пароля — выводится модальное окно с явным запросом подтверждения. Это защищает пользователей от случайных кликов и социальной инженерии.

## 5. Защита канала передачи

- **HTTPS / WSS.** В production окружении трафик обязан проходить через TLS. Заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` принуждает браузеры использовать HTTPS.
- **Заголовки безопасности** (middleware `security_headers_middleware` в `main.py`):
  - `X-Content-Type-Options: nosniff` — запрет MIME-sniffing
  - `X-Frame-Options: DENY` — защита от clickjacking
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Permissions-Policy` — доступ к камере/микрофону/демонстрации экрана разрешён только этому домену
  - `X-XSS-Protection: 0` — отключаем устаревший XSS-фильтр (используем CSP-подход)
- **CORS.** Список разрешённых origin задаётся через переменную окружения `CORS_ORIGINS`; кросс-доменные запросы с произвольных доменов блокируются.

## 6. Защита от XSS и инъекций

- React по умолчанию экранирует все текстовые узлы; `dangerouslySetInnerHTML` в проекте не используется.
- Содержимое сообщений, имена файлов и пользовательские поля выводятся через `{value}` без `dangerouslySetInnerHTML`.
- Парсинг ссылок выполняется регулярным выражением, ссылки рендерятся через `<a target="_blank" rel="noopener">` — атрибут `noopener` блокирует доступ к `window.opener`.
- SQL-инъекции исключены за счёт использования ORM **SQLAlchemy** с параметризованными запросами; «сырых» SQL-выражений в коде нет.
- Все идентификаторы — **UUID v4**, что исключает перебор и предсказуемость.

## 7. Безопасность WebRTC и медиа

- WebRTC-соединения устанавливаются напрямую между браузерами (peer-to-peer); серверу передаются только сигнальные данные (SDP, ICE candidate). Видео- и аудиопотоки не проходят через сервер.
- ICE-серверы — публичные STUN от Google. В production рекомендуется развернуть собственный TURN-сервер для NAT-traversal.
- Потоки шифруются на уровне SRTP/DTLS — это требование стандарта WebRTC, реализуется браузером.
- Доступ к микрофону, камере и захвату экрана запрашивается через стандартный пермишн-диалог браузера и ограничен `Permissions-Policy`.

## 8. Безопасность загружаемых файлов

- Файлы сохраняются под уникальными UUID-именами в каталог `uploads/`, исходное имя хранится только в БД — это исключает атаки через путь (path traversal) и перезапись.
- Доступ к загрузке требует валидного токена и членства в чате (проверка `ChatMember`).
- Тип файла определяется по `content_type`; voice-сообщения дополнительно идентифицируются по префиксу `voice_` в имени.

## 9. Защита запланированных сообщений и опросов

- Просмотр и отмена запланированных сообщений доступны только их автору (`Message.sender_id == current_user.id`).
- Голосование в опросах требует аутентификации; для не-анонимных опросов список голосующих доступен другим участникам, но в анонимных он скрывается на уровне сериализатора.
- Отправка опроса проходит через `WebSocket-диспетчер`, поэтому сразу же транслируется всем активным членам чата без задержек брокеров.

## 10. Журналирование и аудит

- Каждое сообщение хранит `sender_id` и `created_at` — это даёт прослеживаемость действий пользователей.
- Связи `ChatMember.last_read_message_id` фиксируют, кто и до какого момента прочитал переписку (используется для расчёта галочек «прочитано»).
- Ошибки в фоновом воркере планировщика логируются в stdout сервера для последующего разбора.

## 11. Рекомендации по эксплуатации

- В production развернуть **HTTPS-прокси** (nginx / Traefik) перед FastAPI и направить весь трафик через него.
- Сменить значение `SECRET_KEY` на сгенерированное случайным образом длиной ≥ 64 байт.
- Ограничить доступ к серверу БД с помощью `pg_hba.conf`, разрешив подключения только от приложения.
- Настроить регулярные **резервные копии PostgreSQL** (`pg_dump`) и каталога `uploads/`.
- Для критичных учётных записей (super_admin) рассмотреть подключение **2FA через TOTP**.
- Развернуть собственный **TURN-сервер** (например, coturn) внутри корпоративного контура для прохождения NAT в WebRTC.
